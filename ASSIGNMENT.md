# ДЗ 2. Локальный ML-пайплайн

Соберите локальный пайплайн **PostgreSQL → Airflow → MLflow**: чтение данных, проверка, подготовка выборок, обучение и сохранение модели. После клонирования вашего репозитория другой человек должен повторить обучение и загрузить модель для прогноза, а по эксперименту — найти исходный запуск Airflow и снимок данных.

Работа индивидуальная, на CPU. Модель опоздания доставки Olist уже готова; улучшать алгоритм и добиваться заданной метрики не нужно.

## Что выдано

В `prototype.ipynb` и `src/olist_model.py` есть обучение, преобразования признаков и разбиение по времени. В `data/` лежит фиксированный набор Olist с описанием и лицензией. Compose содержит PostgreSQL с автоматической загрузкой данных и Airflow с примером `example_one_task`.

Ваша часть — функции в `src/olist_pipeline.py`, DAG и сервис MLflow. Выданные `data/`, `src/olist_model.py` и `src/check_model.py` оставьте без изменений.

## 1. Поднимите окружение

Нужны Git и Docker Compose v2. Создайте свой репозиторий из содержимого выданной папки и из каталога с `compose.yaml` выполните:

```bash
cp .env.example .env
docker compose up -d --build
```

Дождитесь готовности Airflow на `http://127.0.0.1:8080`, включите и запустите `example_one_task`. Состояние сервисов смотрите через `docker compose ps`, ошибки — через `docker compose logs --tail=100 airflow`.

Добавьте сервис `mlflow`, сохраняя SQLite и артефакты в именованном volume на `/mlflow`. Можно использовать образ `ghcr.io/mlflow/mlflow:v3.16.1`, переменную `MLFLOW_SERVER_ENABLE_JOB_EXECUTION=false` и команду сервиса:

```bash
mlflow server --host 0.0.0.0 --port 5000 --workers 1 \
  --backend-store-uri sqlite:////mlflow/mlflow.db \
  --artifacts-destination /mlflow/artifacts --serve-artifacts \
  --allowed-hosts 'mlflow:5000,localhost:*,127.0.0.1:*'
```

Опубликуйте порт как `127.0.0.1:${MLFLOW_PORT:-5050}:5000`. У MLflow задайте HTTP-healthcheck `/health` через Python `urllib`, а у Airflow — `depends_on.mlflow.condition: service_healthy`, сохранив зависимость от `source`. Примените изменения через `docker compose up -d --build`.

Проверьте MLflow в браузере по `http://127.0.0.1:5050` и из Airflow по `http://mlflow:5000/health`. Адреса подключения уже заданы в `DATABASE_URL` и `MLFLOW_TRACKING_URI`. Оба интерфейса должны быть доступны только на `127.0.0.1`; версии добавляемых зависимостей закрепляйте, без `latest`.

## 2. Реализуйте этапы

Заполните `src/olist_pipeline.py`:

| Функция | Действие и результат |
|---|---|
| `extract` | Прочитать `orders` из PostgreSQL, сохранить обычный UTF-8 CSV (`.csv`), вернуть абсолютный путь строкой |
| `validate` | Проверить непустые данные, обязательные столбцы, уникальность `order_id`, конечные числовые значения и метку 0/1; вернуть путь либо вызвать исключение |
| `prepare` | Разделить данные по времени, как в ноутбуке; вернуть пути к train/validation и метаданные исходного снимка |
| `train` | Обучить готовую модель, сохранить эксперимент и модель в MLflow, вернуть MLflow `run_id` |

Обязательные столбцы: `order_id`, `order_purchase_timestamp`, `price`, `freight`, `weight`, `n_items`, `installments`, `est_days`, `customer_state`, `seller_state`, `category`, `payment_type`, `late`. Описание — в `data/README.md`.

Публичная `validate(snapshot)` принимает путь к CSV и работает только на чтение: без записей, создания каталогов, смены рабочего каталога, сети, БД и запуска процессов.

Адреса и параметры берите из окружения; используйте выданные преобразования, обучаемые только на train. При повторном запуске заменяйте снимок или сохраняйте его в отдельном каталоге запуска, чтобы строки не накапливались.

## 3. Соберите DAG

Создайте DAG `olist_training` с четырьмя отдельными Python-задачами `extract → validate → prepare → train`.

Задайте еженедельное расписание, `catchup=False`, один активный запуск DAG и ограничение времени задач. Для чтения БД нужны повторы с паузой, для `validate` — `retries=0`. У `validate`, `prepare`, `train` оставьте `trigger_rule='all_success'`.

Через XCom передавайте только пути, идентификаторы и короткие метаданные, включая SHA256 снимка. Таблицы и модель сохраняйте в общем каталоге `/opt/olist/work`.

Запустите DAG вручную дважды: оба запуска должны пройти успешно, создать разные run в MLflow и не удвоить данные. Затем временно верните из `extract` испорченную **копию** снимка, например с повторным `order_id`, и выполните отдельный запуск. Он должен остановиться на `validate`, не выполняя `prepare` и `train`. После проверки восстановите код.

## 4. Сохраните и проверьте модель

В каждом MLflow run запишите параметры `epochs`, `seed`, `lr`, `cutoff`, `train_rows`, `validation_rows`, `snapshot_sha256` и метрики `train_loss`, `validation_pr_auc` по эпохам. `cutoff` — граница разбиения, размеры выборок — число строк.

Тег `dag_run_id` должен точно совпадать с `run_id` текущего запуска Airflow из контекста задачи. `snapshot_sha256` — SHA256 байтов исходного CSV `extract`, а не подготовленных выборок; передайте его дальше с метаданными.

Сохраните модель вместе с преобразованиями через `save_predictor` и загрузите всю директорию в артефакты run под именем `model`. Подставьте MLflow `run_id` в готовую команду, которая загрузит модель и выведет пять прогнозов:

```bash
docker compose exec -T airflow python -m check_model --run-id RUN_ID
```

В другом запуске временно сломайте `train` исключением. Исправьте код и выполните Clear только для `train`: обучение должно завершиться без повторного выполнения успешных предыдущих задач.

Перезапустите сервисы, затем пересоздайте MLflow, сохранив volumes:

```bash
docker compose restart
docker compose up -d --force-recreate --no-deps mlflow
```

После готовности MLflow повторите прогноз с прежним `run_id`: модель, метрики и прогнозы должны сохраниться. Не используйте `down -v`, удаляющий volumes.

Необязательно: настройте `epochs` и `seed` через Airflow Params или `dag_run.conf`, сохранив значения по умолчанию, и проверьте другие значения в MLflow. Для 100 баллов это не требуется.
